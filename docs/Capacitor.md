# Capacitor (Mobile + Desktop)

The Instafy frontend (`packages/frontend`) can be packaged as native apps using Capacitor.

The generated native projects live in `packages/frontend/ios` and `packages/frontend/android`.

For the OTA direction and control-plane plan, see:

- `docs/OTA-Rollout.md`
- `docs/OTA-Control-Plane.md`

## Setup

From the repo root:

```bash
pnpm -C packages/frontend install
pnpm -C packages/frontend build
pnpm -C packages/frontend cap:sync
```

Capacitor builds run a production Vite build. Put the selected deployment's browser-safe Supabase
URL and anon key in `$INSTAFY_ENV_DIR/packages/frontend/.env.production.local` (generated by
`scripts/set-capacitor-frontend-env.mjs` when `INSTAFY_ENV_DIR` is set); never put a
service-role key there.

Live updates are wired through `@capawesome/capacitor-live-update` in `packages/frontend`.
The Instafy controller remains the source of truth for release checks and OTA lifecycle events;
the Capawesome plugin is used only for device identity, download, staging, rollback detection,
and reload. After changing OTA plugin dependencies or config, rerun `pnpm -C packages/frontend cap:sync`
so the native projects pick up plugin changes.

## Iteration

```bash
pnpm -C packages/frontend cap:sync
pnpm -C packages/frontend cap:open:ios
pnpm -C packages/frontend cap:open:android
```

Quick local verification (macOS + Xcode):

```bash
pnpm test:ios:config
pnpm test:ios:build
pnpm test:android:config
pnpm test:android:build
```

CI should run the same config, sync, and native build checks shown above. Signing and store
publication are deployment responsibilities.

## Android note (Java)

Android Gradle sync currently requires a supported JDK (recommend Java 17/21). If you have a newer
JDK installed (e.g. Java 25), Gradle may fail with `Unsupported class file major version 69`.
Point Android Studio (or `JAVA_HOME`) at Java 21 and re-sync.

You do not need Java locally for normal web/controller work. Java is only required when you want to
build or debug the native Android project on your machine. CI now installs Temurin Java 21 and the
Android SDK automatically for `pnpm test:android:build`.

The repo now includes:

- `scripts/check-android-config.mjs` for static Android drift checks
- `scripts/test-android-build.mjs` for a local/shell build path that:
  - resolves `ANDROID_SDK_ROOT`/`ANDROID_HOME` or falls back to `~/Library/Android/sdk`
  - runs `pnpm -C packages/frontend cap:sync`
  - runs `./android/gradlew :app:assembleDebug`

## Real-device Android debugging

For physical Android debugging, use `adb` plus the local Capacitor project. The native toolchain builds and installs the app; the repository proof script then verifies that the phone is actually running those synced debug assets rather than a retained OTA bundle.

Recommended setup:

- Android Studio installed
- Android SDK platform tools available (`adb`)
- Java 17 or 21 selected in Android Studio / `JAVA_HOME`
- Phone connected over USB with `Developer options` and `USB debugging` enabled

Basic workflow:

```bash
adb devices
pnpm -C packages/frontend cap:sync
cd packages/frontend/android
./gradlew :app:installDebug
```

After installation, run the fixture-independent debug OTA proof from the repository root:

```bash
node scripts/android-debug-ota-proof.mjs

# Select a phone explicitly when adb lists more than one ready device, and retain the report:
ANDROID_DEVICE_SERIAL='<adb serial>' \
  ANDROID_OTA_PROOF_REPORT='tmp/android-debug-ota-proof.json' \
  node scripts/android-debug-ota-proof.mjs
```

The command requires a debuggable `dev.instafy.studio` APK, one ready USB-debugging device (or `ANDROID_DEVICE_SERIAL`), Playwright dependencies, and a current `pnpm -C packages/frontend cap:sync`. It resolves `adb` from `ANDROID_ADB`, `PATH`, `ANDROID_SDK_ROOT`/`ANDROID_HOME`, or the usual user SDK directories. It does not require login, a controller, a project, or a conversation fixture.

The proof opens `/studio`, accepts the normal signed-out redirect to `/login`, waits 12 seconds, and verifies all of the following before and after a force-stop/cold relaunch:

- `InstafyRuntimeConfig.disableNativeOta` is `true`.
- `LiveUpdate.getCurrentBundle().bundleId` is `null`.
- The exact module entry named by the synced `index.html` was requested as a script. Its served bytes and those of the emitted `StudioRoute` chunk exactly match `packages/frontend/android/app/src/main/assets/public/assets`. A separately emitted `StudioProviders` chunk is also checked when present; builds may include it inside `StudioRoute` instead. Their SHA-256 hashes are included in the JSON output.
- `files/_capacitor_live_update_bundles` contains no retained bundle directory.

The bounded asset probes fetch bytes without executing lazy modules or sending credentials. Each asset's `observedBeforeProbe` distinguishes resources the page requested from explicit probes; `standaloneStudioProvidersAsset: null` means the synced build emitted no separate provider chunk. This proves served asset identity, not successful login or an authenticated Studio mount. Missing emitted files, HTTP failures, and wrong bytes (including an HTML fallback) fail the proof. Run its credential-free regression tests with `node --test scripts/android-debug-ota-proof.test.mjs`.

`shared_prefs/CapawesomeLiveUpdate.xml` may be recreated by plugin initialization with a null current bundle. Its presence is reported for diagnostics and is **not** a failure; a selected bundle id or retained bundle directory is the failure condition. Use `ANDROID_OTA_PROOF_WAIT_MS` only when a slower phone needs a longer observation window, and `ANDROID_APP_ID`/`ANDROID_MAIN_ACTIVITY` only when validating a deliberately renamed debug application.

Useful commands while debugging:

```bash
# launch the app
adb shell monkey -p dev.instafy.studio -c android.intent.category.LAUNCHER 1

# open a deep link directly
adb shell am start -W -a android.intent.action.VIEW -d 'instafy://auth'

# watch logs
adb logcat | rg 'instafy|chromium|Capacitor|ActivityTaskManager'

# capture a screenshot from the real phone
adb shell screencap -p /sdcard/instafy-screen.png
adb pull /sdcard/instafy-screen.png /tmp/instafy-screen.png
```

Notes:

- `./gradlew :app:installDebug` is the fastest path when you need native Android changes on-device; OTA is not enough for manifest/plugin/native Java changes.
- Debug launches clear retained Live Update preferences/bundles in `MainApplication`, then the embedded app checks `InstafyRuntimeConfig` before any JavaScript OTA lifecycle. This second guard is required: native cleanup alone allows the embedded app to download and reselect the stable OTA immediately. Release builds return `disableNativeOta: false`, and older binaries that do not expose the bridge keep normal OTA behavior.
- If the app is already installed from Play internal testing, a debug install may replace it and reset local app data.
- GitHub/Supabase login debugging is most reliable on a real phone, not just the emulator, because Chrome Custom Tabs and deep-link return behavior can differ from the emulator.
- If `adb devices` shows the phone as `unauthorized`, unlock the phone and approve the USB debugging prompt.
- If the app appears to ignore fresh frontend changes, rerun `pnpm -C packages/frontend cap:sync` before reinstalling.

## Android release boundary

Use `pnpm test:android:config` and `pnpm test:android:build` as the public validation path. A
release pipeline may then build a signed AAB and upload it to the selected Play track. Keep the
service-account credential and signing keystore in the deployment secret store; neither belongs in
the repository or frontend environment.

## Auth note (Supabase redirects)

Native builds use a deep link callback (`instafy://auth`) so OAuth (GitHub) can return to the app
instead of leaving you in Safari/Chrome. The callback URL is defined in
`packages/frontend/src/auth/nativeAuth.ts`.

To make this work end-to-end:
- Ensure `instafy://auth` is allowlisted in Supabase Auth “Redirect URLs” (local dev is in `supabase/supabase/config.toml`).
- Ensure the native projects register the `instafy` URL scheme (iOS `Info.plist`, Android `AndroidManifest.xml`).

## Push notifications (iOS)

The native iOS build defers the system notification prompt until you opt in (Studio top bar) or
after a few chat messages (toast nudge).

To send native push notifications from the runtime controller, configure APNs on the controller:

- `APNS_KEY_ID`, `APNS_TEAM_ID`, `APNS_BUNDLE_ID` (required; match the provisioned app)
- `APNS_PRIVATE_KEY_B64` (or `APNS_PRIVATE_KEY`)
- `APNS_USE_SANDBOX=1` for local/dev builds

See `.env.apns.example` (or `.env.supabase.example`) for the full list.

Notes:
- Real APNs delivery requires a physical device + provisioning with Push Notifications enabled.
- You can still test delivery on the iOS simulator via `xcrun simctl push`.
- Android push token registration is disabled until an FCM transport is available;
  the Android in-app notification center still works.
- See [Notifications](Notifications.md) for the durable outbox, account-scoped
  preferences, native notification actions, and provider verification checklist.

## Shake-to-report diagnostics

Shake to report is opt-in under Studio's **Diagnostics** menu. The iPhone shell uses
its native motion bridge; web motion events are a fallback. **Simulate shake event**
exercises the frontend event-to-dialog path, while **Test report dialog** bypasses
gesture detection. Neither proves that the physical accelerometer is delivering events.

An enabled shake attempts to attach the current screen before opening the report.
Screenshot preparation has a three-second deadline: if it stalls or fails, the report
still opens without a screenshot and shows an explanatory status. A late capture cannot
replace screenshots in a newer report. The existing opt-in choice is unchanged.

When investigating a device, distinguish no detected gesture, no dialog, and a submission
error. Check the Diagnostics detection status and app logs first; physical shake detection
still requires verification on a phone, even when the simulated-event test passes.

## iOS release boundary

The mobile sidebar paints to every screen edge, with safe-area padding around its controls.
While this drawer is open, iOS temporarily overlays its status bar on the WebView; closing the
drawer restores its previous status-bar overlay mode (normally non-overlay). Android and the
static startup policy are unchanged. Verify opening, closing, rotating, and returning from a
native screen on an iPhone, including the top status area and bottom home-indicator area.

Use `pnpm test:ios:config`, Capacitor sync, and an unsigned simulator build as the public validation
path. A release pipeline may then build a signed IPA and upload it to TestFlight. Keep the
distribution certificate, App Store Connect credential, and provisioning material in the
deployment secret store. A native TestFlight release should remain the authoritative event before
an iOS OTA bundle is offered for that shell version.

## Physical-Device Debugging

Use the repo helpers instead of piecing together `devicectl`, `tidevice`, WebKit, or mobile test commands by hand.

### iPhone

For physical-device iPhone debugging on a Mac with Xcode installed:

Available root scripts:

```bash
pnpm test:camera:tri-client:smoke:recommended
pnpm ios:device:status
pnpm ios:device:launch
pnpm ios:device:webview -- --json
pnpm ios:device:uitest
pnpm ios:device:capture
pnpm test:ios:camera:smoke
```

What they do:

- `ios:device:status`: show the connected device, lock state, installed app version, and local signing identities.
- `ios:device:launch`: launch `dev.instafy.studio` on the connected iPhone. Pass `--url instafy://...` to open a deep link during launch.
- `ios:device:webview`: start `ios_webkit_debug_proxy` temporarily and list inspectable Capacitor/WKWebView pages for the connected phone.
- `ios:device:uitest`: run the native `AppUITests/AppUITests/testWebViewLoads` test on the connected phone with automatic provisioning enabled.
- `ios:device:capture`: run the same native UI test and export XCTest attachments, including device screenshots, into a local directory.
- `test:ios:camera:smoke`: run the physical-device Camera smoke on the connected iPhone. It opens `Extensions`, uses this iPhone as `Camera`, grants permission if needed, captures a photo, and exports XCTest attachments.

One-time prerequisites on the phone:

- `Developer Mode` must be enabled.
- `Settings > Safari > Advanced > Web Inspector` must be enabled for WebKit inspection.
- Keep the phone unlocked and awake during the first UI-test run.
- A passcode-protected iPhone may require its passcode whenever a new UI-automation session starts. If Xcode reports `Timed out while enabling automation mode`, enter the passcode on the phone and rerun the command. Group related physical checks into one XCTest session to avoid repeated prompts; the UI-test launch keeps the phone awake after the session starts.
- Physical-device UI tests also install a separate runner app, `dev.instafy.studio.uitests.xctrunner`. iOS can require trusting the developer certificate for that runner even when the main `Instafy` app already opens. If the run fails with an `xctrunner` trust or certificate error, trust the developer certificate in `Settings -> General -> VPN & Device Management`, then rerun.
- For `test:ios:camera:smoke`, keep the iPhone unlocked and pointed so the front camera can see something if the rear camera is obstructed.

Signing note:

- `ios:device:uitest` and `ios:device:capture` use `xcodebuild ... -allowProvisioningUpdates`.
- The helper auto-detects the team id from the installed app when possible.
- If that fails, set `IOS_DEVELOPMENT_TEAM` or pass `--team <TEAM_ID>`.

### Android

For Android native bring-up:

```bash
pnpm test:android:build
pnpm --dir packages/frontend test:android:camera:smoke
```

Use the Android camera smoke when you want the real phone-camera provider path, including `Extensions -> Camera`, project attachment, permission readiness, a live `@octo take a photo` request, the Android camera activity, and the return path back into Instafy with saved capture metadata.

Recommended Camera test lanes:

- Regular multi-device regression lane: `pnpm test:camera:tri-client:smoke:recommended`
- Android hardware-only lane: `pnpm --dir packages/frontend test:android:camera:smoke`
- Full physical two-device lane: `pnpm test:camera:tri-client:smoke:two-devices`

The recommended lane uses Android hardware plus the iPhone simulator. Reserve the full physical two-device lane for final hardware confidence, because Apple’s physical-device XCTest runner trust and automation gates can fail before the Instafy Camera flow even starts.

Camera operator model:

- `Use This Device` attaches the current phone app instance as a Camera device for the open space.
- Each phone app instance is its own provider id, for example `camera:<device-id>`.
- If multiple Camera devices are attached, `Manage` lets you choose the preferred default device for new requests.
- Browser and Electron requests route to that preferred Camera device by default.
- For real capture, Instafy now uses an in-app camera surface. The app should stay foregrounded while the request is claimed and the human takes the photo.

Camera device behavior in `Extensions`:

- Each phone app instance registers as its own Camera provider id, for example `camera:<device-id>`.
- `Use This Device` attaches the current phone as a Camera device for the open space.
- If multiple Camera devices are attached, `Manage` shows the attached-phone list and lets you pick the preferred default device for the Camera family.
- The preferred Camera device is what browser/Electron requests route to by default.
- If the preferred phone is offline, lacks permission, or is busy with another request, chat and `Extensions` should now surface that state instead of silently falling back to another device.

For local-stack validation on a physical Android device, use the local controller + Supabase stack, then reverse the ports before launching the smoke:

```bash
pnpm controller:up
adb reverse tcp:8788 tcp:8788
adb reverse tcp:54321 tcp:54321
```

The camera smoke now supports a dev-only guest entry for this path, and the Android debug manifest allows cleartext HTTP so the device can talk to the reversed local services without changing the release manifest.

## OTA packaging boundary

The public repository provides `pnpm ota:bundle`, `pnpm ota:release-payload`, and
`pnpm ota:signing:keygen`. A deployment pipeline can use those primitives to build and sign the web
bundle, upload it to an immutable artifact URL, register the release, and update a channel. Keep OTA
rollout attached to an authoritative native release event; an infrastructure or frontend deploy is
not a mobile release event.

Guard automated OTA registrations with `--required-native-build <exact-build>` from the verified
native publication receipt. The client reports the installed `App.getInfo().build`, separately
from its marketing version and current web bundle. The controller and updated client require
an exact match for guarded offers. An older client that omits this field needs a native update
containing build reporting before it can receive guarded OTA; do not weaken the guard to enroll it.
The guard does not replace native bridge/config/dependency compatibility evidence or embedded
public-key verification. Channel configuration and stable-promotion policy are unchanged.

Vite compiles the normalized channel into `instafy-native-ota-channel:<channel>`; the runtime
resolver derives its channel from that literal. Archive inspection can therefore check the
reachable entry JavaScript against the packaged native `LiveUpdate.defaultChannel`, rather than
trusting environment variables or a separate metadata-only claim. Unconfigured builds still use
`stable`; internal native lanes must explicitly build with `VITE_OTA_CHANNEL=internal` and the
matching native default channel.

The native rollback timer remains armed until React successfully commits the app shell. The
router's initial error fallback and a shell that immediately unmounts do not acknowledge readiness.
This is shell readiness only: authentication/loading UI can count as a successful commit, and
the acknowledgment does not certify network health, later lazy-route chunks, or the complete
Studio workflow. Verify signed download rejection and timeout rollback on real native builds;
JavaScript tests cannot prove the packaged key or native timer behavior.

## Shared release artifact infra

Mobile OTA and desktop binaries may share one public artifact layer, but keep their metadata and
update protocols separate. Configure the public hostname and object store for your deployment.

## Desktop

The repo also includes a minimal Electron wrapper in `packages/desktop-app` for shipping a desktop
binary that loads the web app.

### Public downloads

Publish desktop installers and `electron-updater` metadata to a public, immutable artifact host.
Versioned installer paths should remain stable, while each update channel has a fixed metadata URL.
The deployment pipeline owns storage credentials and publication policy.

### macOS signing + notarization

macOS will show `"Instafy Studio" is damaged and can't be opened` if the app is not properly signed/notarized.

Short-term workaround (dev/test builds):

```bash
xattr -dr com.apple.quarantine "/Applications/Instafy Studio.app"
```

Proper fix for release builds: sign with a Developer ID Application certificate, notarize with App
Store Connect credentials, staple the ticket, and verify the final archive. Keep all signing and
notarization credentials in the deployment secret store.
